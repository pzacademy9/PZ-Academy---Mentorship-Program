# Attendance, Results and Permanent Student ID: design

Date: 2026-10-27. Status: draft for owner approval.

## Why

Today attendance and quiz results run in a separate Google Apps Script system
(`PZ Academy Attendance System/`: `Code.gs`, `Admin.html`, `Attendance Portal.html`)
with a separate admin page and a hand-built "portfolio" Google Sheet per course.
The owner wants to cut that system off and run all of it inside the PZ Academy app.

The core pain: a student gets a new ID in every course (pattern
`FirstName-Profession-Serial`, e.g. `Hamid-Dr28`), generated by hand, shared as a PDF
in a WhatsApp group, typed into Kahoot as the nickname. Results cannot follow a
person across courses, so there is no way to find "the best student over six months".

## Goals

1. One permanent ID per person, created automatically at their first registration,
   reused for every course, webinar and workshop. All attendance and quiz results
   hang on that person.
2. Attendance inside the app: live check-in per session, per-batch percentage, feeds
   certificate eligibility.
3. Quiz results inside the app: upload the Kahoot report, match to students, review
   problems, save per session; combined ranking per batch computed live (replaces the
   sheet's "Combined Master").
4. Public home-page sections for Attendance, Results, Certificates, beside the
   existing Courses / Webinars / Workshops / Mentorship cards.
5. Automatic pre-session emails (Zoom link + the student's ID, optional extras).
6. Longer-term recognition: a fair "best student over a period" ranking across courses.

## Non-goals and anti-goals

- No student accounts are required. No student has one today. Everything must work
  for a person who has only an email address.
- No Kahoot API integration. The admin uploads Kahoot's report file.
- The certificate app and its Firestore stay as they are (read-only; free plan, reads
  are precious, see `src/lib/certs/cert-source.ts`).
- Failure condition: a student silently losing attendance or a score because of a
  typo, a Kahoot rejoin, or two people sharing a name. The system must surface
  every mismatch to an admin, never guess silently.
- Anti-goal: recorded-lecture students leaking into live leaderboards or the live
  competition.

## Decisions made by the owner

- **Identity is the email.** The short ID is a code that points to the email. Students
  type the ID as their Kahoot nickname (Kahoot's separate "player identifier" box
  rejects `@` and digits, so email cannot go there; the owner's plan does have the
  player identifier setting).
- **Rejoin rule.** Kahoot blocks a reused nickname, so a student re-enters the ID with
  `n` added (`...n`, `...nn`). The system reads that as the same student.
- **Duplicate entries for one student in one quiz:** the app alerts the admin and asks,
  each time, "merge (add) the scores, or keep one". Both options must exist.
- **Forgotten or wrong ID:** goes to a review list; the admin resolves it. The
  identifier box asks for the full name (letters only) as a backup signal.
- **Results are fully public.** Anyone can see anyone's scores and the leaderboards on
  the website. Names and scores only, never emails.
- **Students look at "my totals"** (attendance and results across everything) by ID.
- **Attendance check-in.** One-tap personal link in the email. A shared link, posted in
  the WhatsApp group, must also work for anyone without the email or an account: they
  type their email and are checked against the batch's registrations.
- **Session email (automatic, before each class):** the Zoom link and the student's ID
  always included. The Kahoot link is an option, off by default (it is always posted in
  the group). The attendance link is an option.
- **Group sharing of IDs:** a per-batch page (for example "PPC Batch 3: find your ID").
  A student searches their name and sees their ID with a partly hidden email. The
  admin can also download a PDF of the batch's IDs.
- **Live vs recorded students are separate.** Only live students count for live
  attendance, quiz results shown on leaderboards, and "best student". Recorded
  students still get a permanent ID and a certificate, and their quiz tracking stays
  on (it shows in their own totals), but they are excluded from the live competition
  and leaderboards. The app already has `landing_registrations.mode in ('live','recorded')`.
- **Past scores and past attendance must be imported, carefully.** Old quiz results
  and old attendance from the legacy sheets are part of the project (see part 5), not
  an optional extra. They feed the permanent record, "my totals", the public pages
  and the six-month ranking.
- **Attendance is visible** to the student on their own page and on the public page,
  looked up by ID, the same way results are. (Owner decision 2026-10-27.)
- **Old students** get permanent IDs too. Their old IDs (like `Hamid-Dr28`) are kept as
  aliases so old results still match.

## My calls (owner has not confirmed these; flagged on purpose)

- ID format: first name plus a unique 4-digit number (`Hamid-4821`), always ending in
  digits so a letters-only suffix can be read as a rejoin. The profession is dropped
  from the ID. The system guarantees uniqueness, so two people with the same name and
  profession cannot collide.
- Matching ignores case and spaces. The review step suggests students by the full name
  from the identifier box, and remembers each admin fix as an alias.
- Attendance and quiz are kept separate (a quiz does not prove presence). A student who
  took the quiz but has no check-in is flagged; one admin click marks them present.
  The app never marks present silently.
- "Best student over a period": quiz score as a percentage of the top possible score,
  averaged over the period, live students only, with attendance as a gate (for example
  at least 75%, the same bar as certificates) rather than extra points. The owner has
  not approved the formula.
- Check-in window stays as the old system: opens 15 minutes before, closes 15 minutes
  after the session start, with an admin override of auto / force open / force closed.
- The 75% certificate threshold stays admin-configurable.

## What exists already (so the builder reuses it)

- `landing_registrations`: name, email, `mode` (live or recorded), `status`
  (paid / free count as enrolled), `student_id` (nullable link to `profiles`). This is
  the source of "who is in this batch".
- Participant messaging (Brevo templates, sends, recipients, email preferences, in
  migration 0077) is the way to send the session emails.
- A `public.attendance` table (`student_id` to `profiles`, `course_id`, `session_date`)
  and an admin Attendance tab on the student record. It is keyed to app accounts, which
  most students do not have, so the builder decides whether to extend it or add a new table.
- Students and Certificates admin pages (merged).
- Legacy Apps Script: event and session config (Script Properties), check-in rules,
  `_checkinHandler` and the Kahoot-matching logic in `Code.gs`. It is a behaviour
  reference, not code to keep.

## The five parts

1. **Identity, ID pages, session emails.** Permanent ID per email, created at first
   registration, including a one-off backfill for existing students; aliases table; the
   per-batch "find your ID" page and PDF; automatic session emails with the options above.
2. **Attendance.** Sessions per batch (date, time, Zoom link, optional Kahoot link),
   personal one-tap link plus the shared-link fallback, window rules, per-student and
   per-batch percentages, flag for "quiz taken, no check-in", certificate-eligibility gate.
3. **Quiz results.** Upload the Kahoot report file (the main tab: Rank, Player, Total
   Score, Correct, Incorrect), a review screen (duplicates to merge or keep one, unknown IDs
   to suggestions, recorded-student rows tagged), save per session, live combined
   ranking per batch with a predicted top list.
4. **Public pages.** Home-page cards for Attendance, Results and Certificates; public
   leaderboards per course; "my totals" by ID.

5. **Careful import of history.** Bring in old courses, webinars and workshops from
   the legacy Google Sheets. Sources: the event list and sheet ids in the legacy
   Script Properties (`EVENTS_JSON`), each event's attendance sheet (rows carry
   timestamp, name, email, session number) and each portfolio sheet (a Participants IDs
   tab mapping email to the old ID, plus one tab per quiz day and a Combined Master).
   Rules: run per event; show a dry-run report first (counts, unmatched old IDs,
   duplicate entries, people with several emails) before anything is saved; never
   guess silently, send every doubtful row to the same review screen as part 3;
   idempotent, so running it twice never doubles a score or an attendance row; the
   sheets are only read, never changed or deleted; every imported old ID becomes an
   alias of the person; compare totals against each sheet's own Combined Master as a
   check. Results shown from imported data are marked as imported.

Suggested build order: 1, 2, 3, 4, then 5 (it needs the review screen from part 3 and
the aliases from part 1). Each part ends in something the owner can use.

## Further calls (made after the builder check; all mine, not confirmed by the owner)

- **Facts checked 2026-10-27:** `public.attendance` has 0 rows, so it can be replaced.
  Only 3 paid or free non-test rows exist in `landing_registrations`, so history
  lives only in the old sheets.
- **People model:** one row per person with the permanent ID, and emails in a child
  table (lowercased). One email maps to one person. Part 1 includes a small admin
  "merge two people" tool that repoints attendance and results and keeps the old
  IDs as aliases.
- **ID is immutable.** The number is globally unique (not per name), and the display
  name is editable separately. The ID never changes after it is issued.
- **Rejoin rule:** an exact match on a known ID or alias always wins. Only if there is no
  exact match, trailing `n` characters (and nothing else) are stripped and the match is
  retried. Anything that still fails goes to the review list.
- **Webinars, workshops, courses** all behave the same: each event or batch has one or
  more sessions. A webinar is a batch with a single session.
- **Batch link to registrations:** batch means the landing-page batch that
  `landing_registrations` already points to. A session belongs to exactly one batch. A
  person can be in several batches.
- **Who can use admin screens:** admins only for now. Mentors are out of scope.
- **Public safety:** no opt-out. The "find your ID" search needs at least 3 characters
  and is rate limited. Results and attendance are public by decision.
- **Quiz maximum for the percentage:** an admin-entered maximum score per session,
  defaulting to the highest score in the uploaded file.
- **Re-uploads:** saving a session's results replaces that session's earlier results.
  Earlier review decisions (merge or keep one, and alias fixes) are remembered and
  applied again.
- **Session emails:** timing is set per session by the admin, default 1 hour before,
  sent by a scheduled job. Recorded students do not get live-session emails.
- **Time zone:** one academy time zone, PKT (UTC+5), for session times and the
  check-in window.

## Left to the builder

- Database design (tables, indexes, row-level security) and how the existing
  attendance table is reused or replaced.
- How signed personal check-in links are built and expire.
- How the Kahoot report is parsed (it can contain blank or oddly named columns, as the
  sample sheet does).
- Wording and layout of the public pages, within the app's existing design system.
- The exact mechanics of the history import (part 5), within the rules above.
